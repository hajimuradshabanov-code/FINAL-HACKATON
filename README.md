# AreA 51 - Astronaut Health Monitoring Dashboard

NASA Space Apps Challenge 2026 - *Create health monitoring software*.

Health monitoring software for one crew member on a Mars surface EVA. The first screen answers "how am I right now?" with a single state, and the rest of the app shows why:

1. **Measure** - 6 vitals and 11 suit and environment channels at 1 Hz, each tagged with where it comes from.
2. **Detect** - four detectors on every sample: fixed alert bands, a personal baseline (z-score against the crew member's own norm), a trend forecast and a joint test across vitals.
3. **Advise** - a plain-language action for every warning and critical state, because a question to Earth and its answer take many minutes.
4. **Record** - an alert journal, a 30-minute event timeline, a daily check-in (sleep, mood, blood pressure, glucose) and a footprint map of the traverse.

**Health status** (`src/lib/health.ts`, `HealthStatusCard`) is a category, not a score: *Act now* / *Attention* when a vital is outside its alert band, *Watch* when only the baseline, trend or joint test reports, *Nominal* otherwise, *No data* when no vital of the body is measured. Under each vital the dashboard prints its alert band; the timeline prints n, mean, SD and range of the window. The alert bands are this app's settings, not clinical limits.

**Footprint map** (`src/lib/footprints.ts`, `SurfaceMap`). The walked part of the traverse is drawn as boot prints. The route is divided into 24 stretches; each print stores the time, the heart rate and the worst vital status on its stretch and is coloured by that status, so the map shows where on the route the body was under strain (hover a print for its values). The terrain is schematic and the prints are far larger than life; the map says so.

Below the footprints the card shows **where on Mars** this is: the real global map (Viking MDIM 2.1 colour mosaic, NASA / JPL / USGS, public domain) with the major surface features at their catalogued coordinates - Olympus Mons, Tharsis Montes, Valles Marineris, Argyre, Syrtis Major, Jezero, Hellas, Utopia, Elysium Mons, Gale and the polar caps. The simulated EVA site is drawn in the simulation colour at the InSight landing site in Elysium Planitia, where the simulation's weather data was measured.

## Run

```bash
npm install
npm run dev        # http://localhost:5173
npm run build      # type-check + production build in dist/
npm test           # unit tests (node:test + tsx, no extra framework)
npm run check:sim  # fast-forward the simulator 10 min and assert its invariants
npm run check      # everything above, in order
```

Copy `.env.example` to `.env` to choose the data source or set a NASA API key. `.env` is git-ignored.

- Viewport under 1024 px: full-screen mobile app. 1024 px and up: desktop dashboard with tabs. `?showcase` (or *Menu → Showcase layout*) shows the phone-frame presentation with the timeline chart and 3D suit inspector.
- In the training simulation, press **A** (or use "Inject anomaly" in the Alerts tab) to force a vital out of range and watch the alert flow.

## Data modes

The dashboard opens in the **training simulation** (anomaly injector available): a simulated crew member in the real NASA/NOAA environment, described below.

**Simulated and real data never look alike** (`src/lib/provenance.ts`, `Provenance.tsx`). Provenance has its own colours, which no status uses:

| Mark | Meaning | Look |
|---|---|---|
| `SIM` | generated by the simulator, nothing was measured | violet, hatched, dashed outline |
| `MODEL` | computed by this app from real NASA/NOAA data | blue, solid |
| `FEED` / `SENSOR` / `SELF` | measured or reported | white, filled |
| `NO SENSOR` | no instrument connected, so no value | grey |

The header badge names the mode (**Simulation** or **Live**), and the menu switches between the simulation and live data. Every data card has a strip along its top edge in the same code, and one simulated value marks the whole card as simulated. Every value keeps its own tag, and the timeline is labelled *simulated signal*.

*Menu → Switch to live NASA data* opens **live mode**, where nothing is generated. This build has no instrument on the person or the suit, so live mode shows only what NASA and NOAA are publishing now; every body and suit value shows "—" with the tag `NO SENSOR`.

| Value in live mode | Where it comes from | Tag |
|---|---|---|
| Sol and local time | Mars Sol Date and local mean solar time at Gale crater (Allison & McEwen 2000), from the real clock (`src/data/mars.ts`). | |
| Mars air temperature | Newest sol reported by **Curiosity REMS** (min/max air temperature, sunrise), placed on the current local solar time. Served through `/api/rems` because the public feed does not reliably allow browser requests. | `MODEL` |
| Radiation dose and EVA advice | MSL-RAD background accrued this sol plus live GOES protons carried to Mars (Science tab). A GOES reading older than 30 min counts as no data. | `MODEL` |
| Vitals, suit pressure, O₂, coolant, suit temperatures, radio signal, wind | No instrument is connected, so there is no value. A telemetry backend can supply them (`VITE_DATA_SOURCE=ws`). | `NO SENSOR` |

The choice is remembered per browser; `VITE_DATA_SOURCE` sets the default (`nasa`, `live`, `sim`, `ws`).

## Deploy to Vercel

Connected to a Vercel account (`npx vercel login`, once), deploy with `npx vercel --prod`; Vercel builds the Vite site and turns `api/assistant.ts` into a function. If Vercel's local builders fail on Windows (`EPERM … symlink`), deploy a prebuilt bundle instead:

```bash
npm run build:vercel            # dist/ + .vercel/output (static site + /api/assistant function)
npx vercel deploy --prebuilt    # add --prod for production
```

Set `GEMINI_API_KEY` (and optionally `GEMINI_MODEL`) under Project → Settings → Environment Variables; `.env` is never uploaded (`.vercelignore`).

## Sign in / sign up

The dashboard opens after signing in (`#/login`, `#/signup`), or with *Continue without an account*. The airlock ring around the porthole fills as the form's checks pass and closes when access is granted.

This is **demo authentication with no server** (`src/auth/auth.ts`): accounts live in this browser's localStorage with PBKDF2-SHA-256 password hashes, the session is kept in localStorage ("Keep me signed in") or sessionStorage, and five wrong passwords pause sign-in for 30 s. Anyone with access to the browser can read or replace that data, so it personalises the demo but is not real security, and there is no password reset. The page says so. To use real accounts, replace `createAuth` with a client for an auth backend; the forms only call `signIn`, `signUp`, `beginSession`, `continueAsGuest` and `signOut`.

## AI crew assistant (Google Gemini)

The sparkle button opens a chat backed by Google Gemini (default model `gemini-3.8-flash`). Each question is sent with a short summary of what the dashboard currently shows (vitals and their status, active alerts, space weather), so answers refer to the live state; account data is never sent.

The API key stays on the server. The browser talks only to `/api/assistant` (`api/assistant.ts`), which adds the key and calls Gemini's `generateContent`:

- **Local:** put `GEMINI_API_KEY=…` (and optionally `GEMINI_MODEL=…`) in `.env` and restart `npm run dev`; `vite.config.ts` serves the same handler in dev and preview.
- **Vercel:** add `GEMINI_API_KEY` in Project → Settings → Environment Variables and redeploy; `api/assistant.ts` runs as a serverless function.
- Get a key in [Google AI Studio](https://aistudio.google.com/apikey). **Do not** use a `VITE_` prefix for it: anything prefixed `VITE_` is bundled into the public website.

Until a key is set, the panel shows these setup steps instead of a chat. The endpoint rejects cross-site requests and caps message size, history (12 turns) and answer length, but it has no per-user rate limit: anyone using the deployed site spends your Gemini quota, so set a quota or budget alert in Google Cloud.

## Real NASA data

Live mode and the training simulation (`VITE_DATA_SOURCE=nasa`) both feed the dashboard with live NASA/NOAA data; the InSight row below applies to the simulation only, live mode uses Curiosity REMS instead (`src/data/nasaApi.ts`, `src/data/nasaSource.ts`):

| Feed | Endpoint | Drives |
|---|---|---|
| InSight Mars weather (archive: InSight ended in 2022) | `api.nasa.gov/insight_weather` | outside temperature *modelled* as a diurnal curve from a real sol's min/avg/max, wind + gusts |
| GOES proton flux (NOAA SWPC, used by NASA CCMC) | `services.swpc.noaa.gov/json/goes/primary/integral-protons-1-day.json` | solar-proton dose on Mars (≥100 MeV channel, scaled from Earth to Mars), S-scale storm level |
| MSL-RAD surface dose rate (0.67 mSv/sol, Hassler et al. 2014) | published constant | cumulative radiation dose baseline |
| DONKI space-weather notifications | `api.nasa.gov/DONKI/notifications` | NASA data card |
| DONKI CME analyses (speed, direction, width) | `api.nasa.gov/DONKI/CMEAnalysis` | CME arrival time at Mars, particle source longitude, EVA decision |
| OSDR Inspiration4 blood panels (OSD-569 CBC, OSD-575 CMP) | bundled by `npm run fetch:osdr` (`src/science/osdrData.ts`, SHA-256 recorded) | index of individuality: the evidence for personal baselines |
| OSDR / GeneLab study metadata | `visualization.osdr.nasa.gov/biodata/api/v2` | NASA data card |

Responses are cached in localStorage. Each feed in the NASA card shows how fresh it is: **fresh** (inside its cache TTL, whether it came from the network or the cache), **stale** (a refresh failed, older data shown) or **offline snapshot** (a bundled real response captured earlier). After a failed request the endpoint is not retried for 15 minutes. Set `VITE_NASA_API_KEY` in `.env`: the shared `DEMO_KEY` allows only about 10 requests per hour per IP.

Known external limits: the OSDR endpoint does not send CORS headers, so browsers block it and the card shows the bundled OSDR snapshot; `insight_weather` serves archived data only (and returns 403/429 when the key is rate-limited).

**What is real and what is not (training simulation).** Astronaut vitals (HR, SpO₂ …) and suit sensors are simulated, because no live crew telemetry is public. Outside temperature, wind and radiation dose rate are *modelled* from NASA/NOAA inputs, and visor/glove/boot temperatures are simulated from that same modelled outside temperature. Values carry a provenance tag (`SIM`, `MODEL`, `FEED`) in the suit inspector and the outside-temperature panel. `VITE_DATA_SOURCE=sim` runs fully simulated, and the NASA card then says so instead of loading.

## Science: methods and validation

The **Science** tab has three parts: *Live models*, *Evidence & validation* and *Methods*. Every model, its formula, the published source of each constant and the app's own assumptions are listed in one registry, `src/science/methods.ts`, which the Methods page renders.

**1. Personal baseline instead of only fixed bands** (`src/science/baseline.ts`). Each vital is compared with the crew member's own norm: exponentially weighted mean and variance, kept separately for rest and EVA and stored per account; z-score on a 5 s mean; a deviation is |z| ≥ 3.5 for 4 s. The norm keeps adapting, so a lasting change (adaptation to altered gravity) becomes the new normal after 10 min instead of alarming forever. Fixed bands still run in parallel.

**2. OSDR data is part of a calculation** (`src/science/osdr.ts`). The Inspiration4 crew's blood panels (4 people, 3 pre-flight and 4 post-flight draws) are analysed with a one-way ANOVA: within-person CV, between-person CV and the index of individuality II = CV_I / CV_G (Harris 1974). Result: median II 0.57, 54 % of 26 analytes below 0.6 (where a population range is insensitive for an individual). The day after landing the personal yardstick flags 5 of 91 values and the laboratory range 4, with none in common; on healthy pre-flight values the personal yardstick false-flags 1.1 % and the population range 4.0 %. One draw (CBC, C003, L-92) is misaligned in the published file and is excluded, not repaired. Four people support the approach; they do not define clinical norms.

**3. Self-report score** (`src/lib/checkin.ts`). No score until something is entered. Score = mean of the answered items, each worth 100 / 50 / 0 by guideline category: sleep (AASM/SRS 2015), blood pressure (ACC/AHA 2017), glucose (ADA Standards of Care); mood is a 1–5 self-rating with no clinical cut-off, and says so. The formula and sources are shown in the app. It is a summary of the answers, not a validated clinical index.

**4. Radiation: from GOES at Earth to a suit on Mars** (`src/science/radiation.ts`). GOES measures protons in Earth orbit, so each step is explicit:

| Step | Model | Source |
|---|---|---|
| Where Mars is | JPL Keplerian elements | JPL SSD |
| Magnetic connection | Parker spiral footpoint, Ω·r/v_sw (61° for Earth) | Parker 1958 |
| Longitude | Gaussian in connection angle, σ = 43° | Richardson et al. 2014 |
| Distance | r^-1.9, shown with the 1.0–2.7 range (measured inside 1 au, extrapolated) | Lario et al. 2006 |
| Atmosphere | only protons above ≈150 MeV reach the surface (21 g/cm² CO₂); the ≥100 MeV channel and the measured ≥10/≥100 spectral index are used | Hassler et al. 2014 |
| Slant paths, shielding | range ∝ E^1.77 → Ω_eff = 2π/(1+γ/p); extra x g/cm² → ((21+x)/21)^(−γ/p) | Bortfeld 1997 |
| Dose | Ω_eff · J · S · 1.602·10⁻¹⁰ Gy/s, S = 5.4 MeV cm²/g | NIST PSTAR |
| CME arrival | cone hit test + drag-based model, ensemble of drag and wind speed | Vršnak et al. 2013, DONKI |
| Limits | 600 mSv career | NASA-STD-3001 |

The suit (0.5 g/cm² assumed) passes about 98 % of what the atmosphere lets through: on Mars the atmosphere is the shield. The decision card turns this into *clear / stay near shelter / return to shelter*; its action levels (0.1 and 1 mSv per 8-h EVA) are this app's choices, not NASA flight rules. The model is a conservative order-of-magnitude estimate and is **not validated against surface dosimetry**. Three labelled hypothetical examples show the logic when the Sun is quiet, including an eruption that is connected to Mars but invisible to GOES.

**5. Measured detection performance** (`src/science/validation.ts`, `npm run validate`). The seeded simulator is driven through the same store and detectors as the live dashboard, one scripted disturbance is injected at a known time, and the first report of each detector is recorded: 30 runs × 4 vitals × 3 disturbance types = 360 runs, plus 20 undisturbed 30-minute runs. Settings were tuned on one set of seeds and are reported on another (run of 2026-11-14). Cells: detected · median / 90th-percentile time to detection.

| Disturbance | Fixed band | Personal baseline | Trend forecast |
|---|---|---|---|
| Abrupt jump to warning level (60 s) | 100 % · 4 s / 5 s | 90 % · 7 s / 33 s | 6 % · 7 s / 7 s |
| Gradual drift to warning level (120 s ramp) | 100 % · 105 s / 113 s | 96 % · 70 s / 119 s | 71 % · 48 s / 77 s |
| Shift that stays inside the fixed band (120 s) | 8 % · 80 s / 112 s | 82 % · 24 s / 89 s | 64 % · 22 s / 77 s |
| No disturbance: false alarms per hour | 0.00 | 1.60 | 1.40 |

On gradual drifts the personal baseline reports a median 28 s before the fixed band. It is a trade-off, not a win: fixed bands are fastest on abrupt events and never false-alarm here, but miss anything inside the range. The stream is simulated, so these are properties of the algorithms on this signal model, not clinical sensitivity. The Evidence tab can re-run the whole test on new random seeds in the browser.

## How the simulator works (`src/data/telemetrySimulator.ts`)

One sample every 1000 ms (`setInterval`, cleared on unmount). Each metric is a mean-reverting bounded random walk plus slow sine drift, clamped to a physiological range, so heart rate reads 72, 73, 71 - never 72, 8, 360.

- Heart rate 60-100 bpm, rises during EVA phases. SpO₂ 95-100 %. Body temp 36.3-37.4 °C. Suit pressure 4.2-4.4 psi.
- Hydration drains about 0.1 %/s and refills on random "drink" events. Radiation dose only increases.
- Distance and rover range shrink only while walking (EVA phases). ETA counts the remaining walking time *plus* the rest phases still ahead, so it keeps counting down while the crew rests.
- Every 30-90 s one metric is pushed into warning or critical for 5-15 s (eased in and out, not teleported).
- 120 s of history is back-filled on start so charts are full immediately.

Thresholds for every status colour live in one file: `src/config/thresholds.ts`. Guidance text and self-report rules: `src/config/guidance.ts`.

`npm run check:sim` fast-forwards 10 simulated minutes, prints value ranges, step sizes and the alert journal, and exits non-zero if an invariant breaks (finite values, monotonic dose, one open alert per metric, ETA never jumping up).

Alerts form a journal: when a warning escalates to critical, the warning stays in the list marked *escalated* and the critical alert links back to it; resolving closes it as *resolved*.

## Use your own backend

Set `VITE_DATA_SOURCE=ws` (and optionally `VITE_WS_URL=ws://host:8080/telemetry`) in `.env`. `WebSocketSource` expects one JSON object per message:

```json
{
  "timestamp": "2026-11-14T08:25:03.000Z",
  "sol": 412,
  "heartRate": 72, "spo2": 98, "hydration": 71.4, "bodyTemp": 36.9,
  "suitPressure": 4.31, "radiation": 1.532,
  "signal": -47, "wind": 18, "outsideTemp": -63,
  "roverRange": 12.1, "distanceKm": 11.8, "etaMin": 31, "progress": 0.17,
  "respRate": 15, "o2Tank": 85.2, "battery": 90.1, "coolantTemp": 12.4,
  "visorTemp": -8.0, "gloveTemp": 21.2, "bootTemp": 19.5,
  "evaActive": true, "anomaly": null
}
```

Missing fields fall back to the previous value (shown as "—" until the first value arrives). The sample time comes from `t` (epoch ms), `iso` or `timestamp` (an ISO string without a zone is read as UTC), otherwise from the receive time, so the clock never freezes. No message for 3 s turns the badge to "Signal lost"; the client reconnects with backoff (1 s, 2 s, 4 s … 15 s). For a local simulator, background-tab timer throttling is not reported as signal loss.

## Performance

First load is about 101 kB gzipped JS plus fonts and about 12 kB of images (WebP). Three.js (550 kB minified / 138 kB gzipped) is in its own lazy chunk that loads only when a 3D suit inspector mounts (desktop dashboard and Crew tabs). Vite warns that this chunk is larger than 500 kB. That is expected: switching to named `three` imports did not shrink it measurably, because `WebGLRenderer` pulls in most of the core library, and the chunk is never part of the initial bundle. Live numbers tween in a small memoised component, each metric component subscribes only to its own slice of the stream, and the WebGL context is released when an inspector unmounts.
